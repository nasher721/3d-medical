# Codebase impact analysis: anatomic multiorgan ICU simulator

## Current architecture

Flowstate is a dependency-free browser application using native WebGL and ES modules. `src/app.js` owns DOM composition, event routing, simulation loop, controls, dialogs, and session persistence. `src/physiology.js` owns bounded deterministic state and derived metrics. `src/anatomy.js` owns the WebGL renderer, local organ meshes, procedural vessel centerlines, particles, transparency, and camera views. `src/organ-assets.js` parses a deliberately small embedded-buffer glTF 2.0 subset. `src/monitors.js` draws canvas waveforms, trends, and a schematic LV pressure-volume loop. `src/ui.js` defines intervention/patient field metadata and markup. `src/content.js` contains organ explanations, lessons, model-guide references. `src/styles.css` owns responsive controls and monitor/dialog layouts.

## Affected files and boundaries

### Modify

- `src/physiology.js` (current model at lines 8-19, 46-82, lifecycle at 104-160): add named vasopressor and hypertonic-solution state, validated bounds, renal urine/outflow state, intervention effects, intracranial circulation metrics/dynamics, and any ventilator/Frank-Starling metrics. Preserve existing identities (`CO`, `MAP`, `SV/EDV/EF`, `CPP`, oxygen content, `DO2`) and finite/clamped input behavior. Decide explicitly whether new outputs are instantaneous targets or smoothed state.
- `src/anatomy.js` (renderer lines 72-215; routes lines 120-147): replace or extend schematic intracranial routes with named Circle of Willis/major branch structures at the simulator's scale; add tissue perfusion/urine-flow route groups and independent per-organ transparency. Existing `layers` is global (`transparent` boolean), route groups are `heart`, `pulmonary`, `brain`, `renal`, and all vessel geometry is generated by `_route`; rendering order currently handles tissue translucency globally (lines 181-195).
- `src/app.js` (composition/event loop lines 17-81; controls/readings lines 84-145; session data lines 130-145): expose independent brain/lung/kidney transparency controls, new intervention controls, live cerebral/renal/ventilator/Frank-Starling readouts, and update renderer metrics. Extend `sessionData`, restore validation, local save/import, and CSV columns for every new persisted setting/metric; preserve versioning or add a migration path.
- `src/ui.js` (intervention metadata lines 31-59): add field definitions and units/ranges/help text for named agents, hypertonic solution, ventilator controls, and any organ transparency controls if represented as field metadata. Existing fields are only norepinephrine/dobutamine/fluid/FiO2/PEEP/RR/tidal volume/ICP plus patient settings.
- `src/monitors.js` (render/update/drawPV lines 17-45): add live Frank-Starling curve view and ventilator display, or generalize monitor mode selection. Existing `pv` is a schematic pressure-volume loop, not a Frank-Starling relationship; monitor update reads `state.metrics` and history.
- `src/content.js` (organ info/lessons/references): document Circle of Willis assumptions, organ transparency interpretation, urine model, intervention assumptions, ventilator model, Frank-Starling curve, and the explicit educational/nonclinical boundary. Add lessons/references only where claims require them.
- `src/styles.css`: size and responsive-layout rules for added controls/monitor panels, transparency switches, renal outflow and curve/ventilator cards across desktop/mobile breakpoints.
- `docs/physiology.md`: specify equations, bounds, state timing, intervention assumptions, urine/outflow and ventilator simplifications, and exclusions. The existing document explicitly says renal flow is not GFR/urine output and excludes fluid elimination, pharmacokinetics, detailed pulmonary mechanics, and clinical validation; new behavior must revise these statements.
- `README.md`: update Explore, model/limits, customization, and anatomical-asset sections to describe the new educational outputs and limitations.
- `assets/organs/README.md`, `scripts/prepare-organs.js`, `assets/organs/anatomy.glb`, `assets/organs/manifest.json`: likely only if new source meshes are shipped (intracranial vessels, renal pelvis/ureter, tissue compartments). The current GLB contains six named surfaces (`brain`, `heart`, paired lungs, paired kidneys) and no internal vessels or collecting system.

### Create or extend tests

- `tests/physiology.test.js`: directional tests for each new agent/solution, ventilator response, urine outflow, cerebral flow, and Frank-Starling output; bounds, reset, finite-output, and scenario coverage.
- `tests/model-consistency.test.js`: extend identity/invariant checks to new state and ensure intervention transitions remain finite and deterministic.
- `tests/anatomical-bundle.test.js`: validate new mesh names/bounds/normals/indexing and renderer route groups/transparency behavior if assets/routes change.
- `tests/organ-assets.test.js`: extend parser fixtures only if GLB schema/assets change.
- A new monitor or integration test may be needed for curve/ventilator render mode, depending on the existing DOM test strategy (current tests are Node-only).

### Existing generated/build surfaces

- `scripts/build.js` copies `assets/organs` into `dist`; any new GLB/manifest must be included there.
- `dist/` is generated output and should be regenerated/verified, not treated as the source of behavior.
- `server.js` is a simple static development server; no backend or external clinical data path exists.

## Integration points and risks

1. **Anatomical fidelity boundary (high):** Current brain routes (anatomy.js lines 128-145) are hand-authored centerlines and do not encode named anterior/middle/posterior cerebral arteries, communicating arteries, or Circle of Willis topology. BodyParts3D surfaces are six external organs only. A visual route replacement needs authoritative source geometry/labels and a stable coordinate convention; do not imply clinical-grade segmentation.
2. **Transparency (medium/high):** `layers.transparent` is one global switch, and tissue draws are sorted as one translucent pass. Independent organ switches require per-organ state and correct depth/blending ordering; route visibility must remain coherent when a tissue is hidden or transparent. Saved layer state must migrate old boolean exports.
3. **Renal physiology scope (high):** `renalFlow` is currently a bounded heuristic (physiology.js line 78) and docs explicitly exclude GFR, urine output, elimination, dialysis, and renal clearance. Adding urine outflow requires a visibly named compartment/output and a deliberately educational relationship, with units and no treatment interpretation.
4. **Interventions (high):** Existing drug effects are algebraic, bounded, and not pharmacokinetic (docs/physiology.md). Adding several vasopressors/hypertonic solutions expands state and event logging; preserve deterministic transitions, reject unknown/nonfinite keys, and avoid presenting dose ranges as clinical dosing guidance.
5. **Cerebral dynamics (high):** Existing brain flow uses CPP, CO2, and optional autoregulation in one bounded equation (physiology.js lines 74-77). New intracranial network visuals must be driven by the same metric/state and not create an unconnected animation. If adding compliance/ICP/flow dynamics, preserve CPP identity and disclose approximation.
6. **Frank-Starling terminology (medium):** Existing monitor `pv` mode is a pressure-volume loop, not a Frank-Starling curve. A curve needs a defined x-axis (preload/EDV or filling pressure), contractility series, current operating point, and a clear distinction between sampled model state and a displayed hypothetical curve. It should not be mislabeled as a clinical ventricular function assessment.
7. **Ventilator model (high):** Current ventilation has FiO2, PEEP, respiratory rate, tidal volume, alveolar ventilation, PaCO2, shunt, and pulmonary vascular load; it lacks mechanics, pressures, modes, alarms, gas exchange time constants, and waveform semantics. New simulator controls should reuse current variables or clearly define added approximations and avoid medical-device claims.
8. **Persistence compatibility (medium/high):** `sessionData` is format `flowstate-session`, version 1; restore requires exact version 1 and validates known patient/intervention keys. New controls require schema versioning/migration or backward-compatible defaults. CSV currently exports a fixed set of metrics and would otherwise silently omit new outputs.
9. **Rendering/performance (medium):** The brain mesh is ~253k triangles and the full GLB ~10 MB; additional vessel meshes/particles and per-organ passes can increase draw calls, GPU memory, and mobile WebGL risk. The custom parser rejects glTF extensions/external buffers, so shipped assets must stay within its subset or the loader must be expanded and tested.
10. **Testing gap (medium):** Existing automated coverage is Node tests for physiology, GLB parsing, and renderer helper logic. No browser automation verifies actual WebGL compositing, controls, or persistence in a browser; visual QA/docs should be part of implementation verification.

## Recommended implementation order

1. Define the expanded state schema, units, bounds, migration, and educational copy; lock invariants/directional tests.
2. Implement model outputs (interventions, cerebral/renal/urine, ventilator, Frank-Starling data) while retaining current metric identities.
3. Implement named intracranial route data and organ-specific renderer layers/transparency; add asset pipeline changes only where internal meshes are truly required.
4. Add app controls, readings, monitor modes, export/import, and responsive styling.
5. Update docs/content, rebuild assets/dist, run checks/tests, and perform browser visual verification at desktop/mobile sizes.

## Scope assessment

Expected direct modifications: 8 existing source/docs/style files plus 2-4 existing test files. Potential new/changed anatomical assets: 3-5 files only if geometry is added. No server/API/database files are implicated. Overall risk is high because the request crosses model semantics, rendering, UI, persistence, and educational safety boundaries.
